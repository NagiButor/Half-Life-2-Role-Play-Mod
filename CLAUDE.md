- Ядро: `game/shared/hl2rpm_crashdebug.{h,cpp}` — чистый Win32 без Source-заголовков (в vcxproj `PrecompiledHeader=NotUsing`; снимает `#define`-запреты `strncpy/_snprintf/fopen`). Собирается в client и server; буфер «крошек» общий через named shared memory `Local\hl2rpm_crashdbg_<pid>`.

- При краше (VEH, до 3 отчётов за сессию, пропускается если подключён отладчик; ловит в т.ч. `int 3` от `Error()`) пишет `hl2rpm\crashes\crash_<время>.dmp` + `.txt` и запускает `hl2rpm\crashtools\analyze_crash.bat` (x86 `cdb` из Windows Kits → `.analysis.txt`). Запасной вариант — `crashtools\run_under_debugger.bat` (игра под cdb, ловит second-chance).
- Для символов PostBuild client/server копирует `.pdb` в `hl2rpm\bin`.
- Добавлять крошки в подозрительный код: `#include "hl2rpm_crashdebug.h"` + `RPM_CRUMB( "fmt", ... )` (дёшево, потокобезопасно). Уже расставлены в пути попаданий: `FireBullets`, `ImpactTrace`, `UTIL_DecalTrace`, серверный `DispatchEffect`, `CBaseHLBludgeonWeapon::Swing/Hit/ImpactEffect`, клиентский `DispatchEffectToCallback` (FX begin/end), `Impact()`/декали, `PerformCustomEffects`, `PlayImpactSound`.
- **Краши при выходе, смене карты и `mat_reloadallmaterials`** (NULL в `filesystem_stdio+0x29313`, 0xC0000374) были следствием переполнения массивов констант shader API (см. «Константы пиксельных шейдеров» ниже) — исправлено 2026-10-01, выход теперь с кодом 0. Если похожий «случайный» краш в чужом модуле вернётся — искать порчу кучи.
- **Поиск порчи памяти — аппаратная точка на запись в cdb** (так найден виновник за один запуск): игра под cdb (`-cf init.txt`, **без** `-g`, иначе скрипт выполнится только при первом исключении), точка в уже загруженном модуле (`bu client!Функция`) ставит `bp модуль+смещение` (до загрузки модуля `bu модуль+смещение` не разрешается), а та — `ba w4 <адрес>` с командой `kb 60; gc`. В строках команд cdb пути к скриптам писать через `/` (обратный слэш съедается как escape), вложенные команды выносить в файлы `$$>< путь`. С `+mat_queue_mode 0` всё рисуется в основном потоке (детерминированно).

## Компиляторы карт HL2RPM (hl2rpm_vbsp / vvis / vrad)

Свои vbsp/vvis/vrad — форк компиляторов Mapbase из `sp/src/utils` (2026-10-30). Новый формат карт невозможен (`engine.dll` читает только BSP v20, дерево BSP нужно ему для коллизий, физики, звука, AI и отрисовки), поэтому это те же инструменты, доработанные под открытый мир и deferred.

- **Сборка и установка**: `powershell -File hl2rpm_extras\tools\install_compilers.ps1` (`-NoBuild` — только копирование). Проекты `utils/vbsp/vbsp.vcxproj`, `utils/vvis/vvis_dll.vcxproj`, `utils/vvis_launcher`, `utils/vrad/vrad_dll.vcxproj`, `utils/vrad_launcher` (v143) кладут результат в `sp\game\bin`; скрипт копирует в `Source SDK Base 2013 Singleplayer\bin` как `hl2rpm_vbsp.exe`, `hl2rpm_vvis.exe` + `hl2rpm_vvis_dll.dll`, `hl2rpm_vrad.exe` + `hl2rpm_vrad_dll.dll` — инструменты работают только из `bin` SDK (`steam.dll`, `filesystem_stdio.dll`), лаунчеры Mapbase грузят `<своё имя>_dll.dll` (нет файла — молча берут стоковый `vrad_dll.dll`). Стоковые exe не тронуты.
- **Hammer++** (`bin\hammerplusplus\hammerplusplus_gameconfig.txt`, пути BSP/Vis/Light) смотрит на `hl2rpm_*.exe`; бэкап до переключения — `hammerplusplus_gameconfig.txt.bak_20261030_043414` (откат — вернуть три строки). `compile_map.ps1` навыка `hl2rpm-hammer` по умолчанию тоже на них (`-Tools stock` — Valve).
- **vbsp**: списки треугольников против трещин T-стыков (примитивы, 65536 индексов на карту — `unsigned short` формата) раздаются после всех граней, крупнейшим первыми; не поместившиеся грани — веером с угла, у которого меньше T-стыков (возможна трещина в пиксель, как у `-notjunc`), в логе их число и площадь. Раньше — `Too many t-junctions to fix up!` и обрыв компиляции (`rpm_trainstation_testoptimization`: 3259 таких граней, 3156 поместились). В конце — **бюджет карты**: доля каждого лимита формата, ≥ 80 % — предупреждение (T-стыки, физика и текст сущностей — не жёсткие лимиты).
- **vvis**: быстрый проход порталов по умолчанию (полный — `-full`: на карте без hint/areaportals часами и всё равно пропускает почти всё), радиус видимости — `-radius N` или `farz` `env_fog_controller`. Тонкое отсечение — в игре (Occlusion culling).
- **vrad**: по умолчанию **плоские лайтмапы** (`g_bDeferredLighting`: свет в точках lightmap не собирается, отскоков нет, амбиент `0.4` серого): deferred лайтмапы не читает (`deferred_brush.cpp` ставит лишь флаги формата). Считаются worldlights (из них сервер делает deferred-лампы, в т.ч. текстурные), амбиент листьев (`-fastambient`), свет detail props. `-full` или `-final` — запечённый свет стокового vrad (для `-nodeferred`). `rpm_trainstation_testoptimization`: 42 с на LDR+HDR против ~12 мин у `-ultrafast`.
- **Assert'ы библиотек** (`mathlib.lib` собрана с assert'ами: `color_conversion.cpp` при свете ярче формата lightmap) больше не открывают модальное окно «Assertion Failed» — только в лог, и одинаковый — один раз (`CmdLib_SpewOutputFunc`, `utils/common/cmdlib.cpp`; окно — лишь при подключённом отладчике).
- Время полной компиляции `rpm_trainstation_testoptimization` (15к граней, 9к листьев): vbsp 16 с, vvis 6 с, vrad 2×26 с. Регрессия на `test_deferred`: все счётчики геометрии совпадают со стоковым vbsp.
- Предупреждение `Error! Invalid VTX file checksum ... combine_smallmonitor001.dx80.vtx` — несовпадение файлов модели в моде (не компилятора).
- **Имя карты — не длиннее 31 символа**: в сохранении движок хранит 31 символ имени (`rpm_trainstation_testoptimization`, 33, обрезается до `..._testoptimizati` → «Save file is not valid», загрузка не работает), `engine->GetLevelName()` — 39 с `maps/`. `hl2rpm_vbsp` предупреждает о длинном имени.

## Компиляция шейдеров (ShaderCompile235)

Исходники `.fxc` лежат в `sp\src\materialsystem\stdshaders`. Компилятор: `sp\src\game\ShaderCompile235\bin\ShaderCompile.exe` (standalone, без perl/DXSDK). Штатные `buildshaders.bat`/`buildepisodicshaders.bat` не использовать — они собирают всё.

```powershell
$sc = "E:\SourceModding\HL2RPMSOURCE\source-sdk-2013-mapbase-v8.0\sp\src\game\ShaderCompile235\bin\ShaderCompile.exe"
cd "E:\SourceModding\HL2RPMSOURCE\source-sdk-2013-mapbase-v8.0\sp\src\materialsystem\stdshaders"
# один шейдер: -ver 30 для *_ps30/*_vs30, -ver 20b для *_ps20b/*_vs20
& $sc -ver 30 -shaderpath . lightingpass_global_ps30.fxc
# только .inc-заголовок (без компиляции комбо): добавить -dynamic
```
Или списком через `process_shaders.ps1 -File <список.txt> -Version 30`.

- **Какой `.inc` видит C++:** в `game_shader_dx9_episodic.vcxproj` include-пути идут `fxctmp9;vshtmp9;include`, т.е. C++ берёт `.inc` из `fxctmp9\` (старый формат, классы `sdk_*`), а ShaderCompile235 пишет новые в `include\` (классы `SDK_*`). При изменении числа каскадов/регистров нужно синхронно править `deferred_global_common.h`, `cascade_t.*`, C++ биндинг констант и `.fxc` (регистры констант пиксельного шейдера ограничены — проверять пересечения `register(cN)`). Структуру `weatherData_t` менять только с пересборкой **обеих** DLL (client + game_shader_dx9).
- CSM: 2–4 каскада, подогнанных под фрустум камеры (practical split), текстел-снэппинг, дальние каскады обновляются реже (`r_csm_stagger`); пресеты — таблица в `cascade_t.cpp` (`r_csm_quality` 0..5, `r_csm_distance_scale`). Каждая перерисовка каскада ≈ полный проход сцены (~2 мс на открытой карте на GTX 960M) — на «Высоком» 2-й каскад обновляется раз в 2 кадра (движение/поворот камеры и сдвиг солнца всё равно форсируют обновление, `ShouldUpdateCascade`). Дальние каскады пропускают объекты с угловым размером < `r_csm_caster_cull` (0.006). Лямбда разбиения: 0.92 (Низкое–Среднее), 0.95 / 0.96 / 0.97 (Высокое / Очень высокое / Ультра; на Ультра первый каскад ~134 ед. с текселем 0.22 ед., второй ~460 ед. с 0.7) — при ~0.78 первый каскад тянулся на 420+ ед. и тени у ног были мыльными; `r_csm_split_lambda` (−1 = из пресета) — для подбора. Тенеобразователи каскадов берутся из **всех** листьев (`r_csm_novis 1` → `ViewSetupVis( true, … )`): по PVS камеры тени стен/пропов вне его мигали при переходе между листьями.
- **Теневые виды видят обе стороны стен**: мировые списки теневых видов строятся с `bShadowDepth` (`r_deferred_shadow_worldlists`) — обычный список отбрасывает грани, повёрнутые от камеры-«солнца», по стороне плоскости BSP (на `$nocull` не смотрит), и стена с nodraw-обратной стороной (vbsp не создаёт там грань) отбрасывала тень только краями; плюс `EnableCulling( false )` в `defpass_shadow.cpp`. Стоит ~+0.8 мс.
- **Тени солнца без `oDepth`**: теневой проход каскадов (и карты дождя) больше не пишет глубину из пиксельного шейдера — смещение даёт растеризатор (`SetShadowDepthBiasFactors( r_csm_slope_bias 0.5, r_csm_const_bias 0.5 текселя, не меньше 1.5 шага глубины )` в `COrthoShadowView::CommitData`, `EnablePolyOffset` всегда включён в `defpass_shadow.cpp`) → работает ранний Z (−20–25% кадра на открытых картах). Прежний наклон 3× отодвигал крутые грани за пол у их основания — светлая полоса у основания стен. **Глубина каскадов солнца 24-битная** (`NV_DST24`, `r_deferred_shadow_ortho_depth24`): движок на NVIDIA даёт теням 16 бит (в консоли `[deferred] shadow depth: hardware 16 bit, sun cascades 24 bit`), а шаг 16 бит на ~13 000 ед. к солнцу ≈ 0.2 ед. — как тексель первого каскада: акне на обращённых к солнцу поверхностях. Прожекторы/точки остаются на формате движка. VS пишет растровую глубину (`vProjPos.z/w`): старая формула `dot(fwd)/zFar` расходилась с матрицей движка на ~2 текселя. **Прожекторы и грани куба точечных ламп тоже без `oDepth`** (`shadowpass_ps30`: глубину пишет только старый DPSM): смещение растеризатора `r_deferred_shadow_proj_slope_bias` (4) / `_depth_bias` (3e-6) задаётся в `CommitData` видов (`SetProjectedShadowDepthBias`) — картинка та же, а тень точечной лампы с гранями 2048² подешевела с ~9.5 до ~2–3 мс (demo_map_rus 57 → 77 FPS за счёт прожекторов). Коэффициенты `SetShadowDepthBiasFactors` действуют на **все** материалы с `SHADER_POLYOFFSET_SHADOW_BIAS` до следующей установки — в основном виде этот вид смещения не использовать (глаза им «проваливались» за сцену).
- **Тени солнца** в `lightingpass_global_ps30.fxc` (`SunShadowPCSS` → `SunShadowCascade`), переписаны 2026-10-02 (A/B со старым шейдером: мутные пятна с полосами внутри полутени и прямоугольник акне на рифлёных воротах map_v11 ушли). **Фильтр — кубический B-сплайн** через аппаратные билинейные сравнения (каждое взвешивает пару текселей по оси): масштаб 1 (σ≈0.58 текселя) — 4 выборки, до 2 — 16; результат — гладкая функция положения, поэтому вблизи (тексель на много пикселей) нет «лесенок» углами и полос по столбцам текселей, как у прежнего диска Vogel. **Нормаль для теней — геометрическая** из буфера глубины: нормаль G-буфера с картой нормалей давала самозатенение по её узору (акне на рифлёном металле). `r_csm_shadow_normal 2` (по умолчанию): по каждой оси берётся сторона, чья линейная экстраполяция 1/z (на плоскости 1/z линейна в экране) предсказывает пиксель, — его собственная поверхность (8 выборок глубины, +0.3 мс); `1` — производные квадрата 2×2 (`ddx/ddy`: на складках смешивают обе поверхности, и разбиение на квадраты меняется при любом сдвиге камеры), `0` — нормаль G-буфера. Шаги экрана (`ddx` интерполянтов) берутся в начале `main`, до ветвлений. **Фильтр учитывает размер пикселя** (`r_csm_footprint` 0.5): масштаб B-сплайна ≥ 0.5 × (сколько текселей карты накрывает пиксель, по тем же шагам к соседям) — издали и под острым углом тени стержней/рёбер мельче пикселя перебирались от текселя к текселю при ходьбе (−30 % мерцающих пикселей, +0.2 мс). **Камера света каскада — в 12 000 ед. к солнцу** (`r_csm_center_origin 0`): вариант «в центре каскада с отрицательной ближней плоскостью» (`1`) отсекал тенеобразователи, стоящие от центра в сторону солнца (отсечение по пирамиде вида не учитывает отрицательную ближнюю плоскость): части теней висящих коробок test_deferred появлялись и пропадали от шага или поворота камеры (A/B по шагам 8 ед.). Снэппинг к текселю и шагу глубины — в double. Смещение — на стороне приёмника: вдоль нормали до `r_csm_bias_normal` (1.5) текселя (запас глубины ∝ tg угла, но у основания стены не пропускает свет) + наклонное `r_csm_bias_slope` (0.25) + 0.1 текселя; плоскость приёмника (dz на тексель, ±6 текселей). PCSS: поиск блокеров (16 взвешенных выборок R32F, `CommitTexture_CascadedDepthRaw`) → радиус полутени = расстояние × tg(0.2665°) × `r_csm_pcss_sunsize`, добавляется к B-сплайну как диск (масштаб = √(1+0.75·p²), ≤ 2); предел — `r_csm_pcss_penumbra` текселей (≤ 3) и одинаковая ширина в мировых единицах во всех каскадах (c71.z); дальние каскады без поиска. Нет блокеров, но аппаратная карта в центре говорит «тень» — фильтр (R32F теряет далёкие тенеобразователи на восходе). Переход каскадов — узкая полоса (smoothstep 0.92–0.995) с **тем же** фильтром следующего каскада (старая полоса 15 % с жёсткими 4 выборками двигалась с камерой — акне «то есть, то нет»). `r_csm_pcss 0` — тот же фильтр без поиска (масштаб 1); 2 — доля блокеров, 3 — сырая−приёмник, 4 — сырая глубина, 5 — сам множитель тени (с `r_deferred_debug_lighting_only 1` — белое альбедо — на экране только тень: так ищется её мерцание); 6 / 7 — видимость неба / SSAO, 8 — содержимое G-буфера (красный — 3D-скайбокс, зелёный — карта, синий — тело игрока). Отладка подгонки каскадов: `r_csm_debug_jitter <ед.>` (случайный сдвиг каждый кадр при неподвижной камере — тени не должны меняться), `r_csm_debug_log 1`. В теневых видах не пересчитываются затухание статических пропов и списки detail props (`UpdateRenderablesOpacity` считал их от камеры света и портил общее состояние); трава detail props попадает только в ближние каскады солнца своим путём (см. «Трава detail-спрайтов»). Внутри `[branch]` только `tex2Dlod( s, float4( uv, z, 0 ) )` (X3528). **Тело игрока в первом лице**: Mapbase обнуляет кости головы/рук только для основного вида, в карты теней идёт вся модель — голова и плечи затеняли видимые ноги/торс. Клиент выставляет `INT_RENDERPARM_DEFERRED_LOCAL_BODY` (слот 17, `public/renderparm.h`) на время отрисовки тела (`C_BasePlayer::DrawModel`), G-буфер пишет маркер 254, проход солнца для этих пикселей игнорирует тенеобразователи ближе `r_csm_body_bias` (36 ед.) — тень тела на земле остаётся, тень стены на теле тоже (если стена дальше). У стен с nodraw-обратной гранью у основания остаётся линия < 1 пикселя (за основанием в карте теней пусто, фильтр его захватывает).
- **Сглаживание** (`r_deferred_aa`: 0 нет / 1 FXAA / 2 TAA, по умолчанию TAA; пункт «Сглаживание» в меню «Графика»). MSAA движка в deferred-виде ничего не сглаживает (композит читает один свет на пиксель — края «лесенкой» и с 8x), а стоит дорого: кадр 18.3 мс вместо 16.2 (GTX 960M, 1600×900), и каждый полноэкранный проход/копия кадра платит за 8 сэмплов ещё раз. Поэтому `DeferredAA_DisableMSAA` (вызов в `CDeferredManagerClient::Init`) один раз за сессию выполняет `mat_antialias 0` — **без** `mat_savechanges`, реестр пользователя не меняется; `r_deferred_disable_msaa 0` оставляет MSAA. **FXAA 3.11** (`hl2rpm_fxaa_ps30`, `DrawDeferredFXAA`; `r_deferred_fxaa_subpix/_edge/_edge_min/_debug`) — ~0.8 мс, тонкие ветки и провода остаются пунктиром. **TAA** (`deferred/deferred_taa.cpp`, `hl2rpm_taa.cpp`, `hl2rpm_taa_ps30`) — ~1 мс:

  - история клиппится к боксу среднее ± `r_deferred_taa_clip` (1.25) σ окрестности 3×3 в YCoCg; вес истории `r_deferred_taa_history` (0.92) / `_history_min` (0.75, где история не сошлась), при быстром движении ×0.8; выборка истории Catmull-Rom (5 выборок), при нулевой скорости — одна;

Проходы TAA рисуются **прямо в кадр**: у рендер-таргетов с `MATERIAL_RT_DEPTH_SHARED` при MSAA заднего буфера свой буфер глубины-трафарета, меток там нет. История — две копии кадра в его формате (RGBA8), поэтому выход дизерится (иначе шаг 8 % «залипает»);
  - накопление джиттера — это бокс-фильтр размером в пиксель поверх фильтрации текстур: текстуры мылились. Композит (`composite_ps30`, c23.w) сэмплирует альбедо со сдвигом мипа `r_deferred_taa_mipbias` (−0.5); альфа-тест — без сдвига, как в G-буфере;
  - отладка `r_deferred_taa_debug` 1 движение / 2 насколько история подтянута / 3 маска оружия / 4 вес истории (красным поверх серого кадра, отдельным проходом — история не портится), `r_deferred_taa_info`, `r_deferred_taa_jitter 0`, `r_deferred_taa_stencil_test`. (вокруг на её уровне земли не видно — глубоко внутри здания; раньше середина большого навеса судилась по его крыше и считалась открытой, а края у стен — закрытыми: инверсия и полоса в тени двора test_deferred под висящим блоком); для навесов выше 128 ед. — плавно карта 512 ед. - **Туман**: композит меряет дистанцию тумана от камеры **текущего** вида (`GetWorldSpaceCameraPosition` в c3), а не от `IDeferredExt::GetOriginBase()` (основной вид): в 3D-скайбоксе (свои координаты, дистанции тумана /16) город был в ~16 000 ед. от камеры и тонул в тумане целиком — плоские силуэты. Цвет классического тумана карты (`CRendering3dView::EnableWorldFog`, `viewrender.cpp`) при активной погоде — погодный (`WeatherRender_GetSkyboxFogColor`, как у скайбокса), кроме `fog_override`: дневной цвет карты ночью заливал всю дальнюю геометрию светящимся серым. Классический туман карты и погодный высотный туман складываются; `fog_override 1` без `fog_color` даёт **чёрный** туман (−1 −1 −1) — для A/B не годится.

- **GI-пробы — непрямой свет, тёмные помещения** (`deferred/deferred_gi.cpp`; шейдеры `deferred_gi_ps30`, `deferred_giblur_ps30`, `deferred_giup_ps30`, `deferred_gi_upload_vs30/ps30`, C++ `stdshaders/deferred_gi.cpp`). **Две сетки** 32×32×10 (ближняя) и 24×24×10 проб, тороидальные вокруг камеры (смещение 0.45 ячейки: пробы ровно на полу были невалидны): ближняя с шагом `r_deferred_gi_spacing` (64; ±736 ед., камера на 3.5 ячейки выше низа) и дальняя с шагом ×4 (256; ±2944 ед., `r_deferred_gi_far`). На пробу 32 луча (длина 1536 × шаг/64, не больше 3072) + лучи к солнцу от попаданий (2560): L1-SH видимости неба и отражённого солнца (цвет × `GetReflectivity()` поверхности), «свободные дистанции» по 6 осям (против протечек сквозь стены), валидность. **Трассировка — в пуле потоков** (`ParallelProcess`, `r_deferred_gi_threads`): только мир (`TRACE_WORLD_ONLY` — BSP-трасса потокобезопасна; статик-пропы и материальная система — нет, поэтому пропы GI не заслоняют, а альбедо попаданий ищется в основном потоке, `FinishJob`). Раньше проба стоила ~0.2 мс в одном потоке при бюджете 1 мс: сетка набиралась полминуты на глазах («тени грузятся чанками»), за идущим игроком не успевала, а за её краем включался старый плоский амбиент («пол тени тёмная, пол светлая»). Теперь: **первый кадр карты** трассирует всё вокруг камеры разом (`r_deferred_gi_load_ms` 1500 — кадр ещё под экраном загрузки), дальше `r_deferred_gi_budget_ms` (1.0) настенного времени на кадр, растущий с очередью до `r_deferred_gi_catchup_ms` (4; идущий игрок открывает ~900 проб/с, телепорт — все), четверть пачки — дальней сетке; новая проба **проявляется** за `r_deferred_gi_fade` (0.35 с; вес в альфе плоскости 2 атласа). Рабочие потоки сами смотрят на часы перед каждой пробой (`s_flJobDeadline`): пачка, отмеренная по средней скорости, иногда выходила за бюджет в разы. Альбедо ищется только у **загруженных** материалов (`IsMaterialLoaded`): `FindMaterial` по имени пропатченной под кубмапу воды, которой в BSP нет, читал диск и падал с ошибкой — по нескольку мс на имя посреди кадра (кадры по 13 мс при ходьбе вдоль воды demo_map и «в 9 раз более дорогая» трассировка). Скорость: 40–400 проб/мс на простых картах, 20–40 на demo_map — `r_deferred_gi_stats` (там же худший кадр трассировки с загрузки карты). Солнце сдвинулось больше `_sun_refresh` (1.5°) — отскок пересчитывается. В RGBA16F-атласы пробы заливаются крошечными квадами (без lock текстур). **На экране**: `deferred_gi_ps30` в половинном разрешении — ближняя сетка, где она кончается или ни одна проба не видит точку — дальняя, за ней — **оценка без проб** (открытая полусфера над поверхностью × видимость неба карты дождя из SSAO-таргета, который поэтому рисуется раньше GI; земля, освещённая солнцем); покрытие всегда 1, старый амбиент остаётся только пикселям неба/3D-скайбокса. Веса проб мягкие (стена «закрывает» пробу на 1/8 шага — жёсткий порог рисовал ячейки сетки на стенах). Блюр учитывает глубину **и нормаль**; затем `deferred_giup_ps30` поднимает до полного разрешения (в blur-таргет, его и читает `lightingpass_global_ps30`, s7): каждый пиксель берёт те из 4 соседних полуразрешённых, чья нормаль — его (каждый посчитан для правого нижнего пикселя блока 2×2). Обычное билинейное чтение давало **светлую линию вдоль каждого ребра брашей** («эффект комикса»: свет соседней грани) и тёмную обводку силуэтов на фоне неба (половина «нет света» неба). Отдельный проход, потому что у `lightingpass_global_ps30` **не осталось временных регистров** (X4505 на любой добавке — не дописывать туда). `r_deferred_gi_sky_boost` (4): амбиент карт был ~3 % солнца — с честной видимостью неба помещения уходили в черноту. Ещё `_bounce`, `_bounce_indoor` (2.5), `_skybounce`, `_fill`, `_min` (0.07), `_leak_tolerance`. `DeferredGI_GetCameraSky()` / `giData_t::vecParams2.x` — видимость неба у камеры (0 в закрытой комнате). Металлы стока - «полуметаллы» (0.45-0.75): они крашеные и ржавые. `r_deferred_pbr_list <подстрока|*>` печатает, что получил каждый материал при загрузке.

- **Вода: собственный цвет, плотность, отражения** (2026-10-11; «вся вода просто прозрачная»). Тестовая карта - `water_test` (10 бассейнов из стоковых материалов, ступени 16/64/128/256 ед.; генератор `hl2rpm_extras/tools/make_water_test.py`, солнце карты = солнцу deferred в 13:00 - для сравнения с `-nodeferred +sv_weather_procedural_sky 0`). Причины и что сделано:
  - `$fogcolor` (и прочие «forward»-цвета, `UpdateForwardMaterials`) **умножался на яркость мира повторно** при каждом пересканировании материалов: с `mat_queue_mode 2` `SetVecValue` применяется позже, и чтение переменной сразу после «возврата оригинала» давало уже масштабированный цвет, который становился «оригиналом» - после загрузки карты (погода ещё вплывает, масштаб 0.3-0.4) цвет воды уходил в чёрный. Оригиналы теперь запоминаются (`AddForwardVar( ..., pKnown )`), масштаб - в гамма-пространстве как `scale^(1/2.2)` (переменные - гамма-цвета; умножение на сам масштаб давало степень 2.2), гистерезис 1 % относительный, раз в секунду значения ставятся заново (перезагрузка материалов).
  - Плотность: сток туманит подводное дважды (в виде преломления и в шейдере воды) - у нас было один раз, вода была вдвое прозрачнее. Теперь `1 - (1 - f)(1 - saturate(f - 0.05))`, f = глубина x путь / (`$fogend` - `$fogstart`); путь луча - с преломлением (1 сверху .. 1.5 под скользящим углом, x 0.8; `r_deferred_water_viewangle`), `r_deferred_water_density`.
  - Цвет воды освещён: буфер света под пикселем (по смещённым волной координатам, 4 выборки), но не меньше «свет неба + `r_deferred_water_scatter` (0.25) открытого света» x видимость неба (G SSAO-таргета) - дно бассейна для неба «яма», а поверхность нет; всё относительно открытого света момента (c11, c12 в `water.cpp`; s6 - буфер света, s7 - SSAO). Раньше - «яркость дна x 8»: над тёмным дном вода была чёрной. Отладка `r_deferred_water_debugview 1..4`, `r_deferred_water_debug 1` печатает `$fogcolor` «сейчас» и яркость мира.
  - Воды без `$reflecttexture` (lowdirty, sewer - у них кубмапа во втором, «дешёвом» проходе) получают отражение в реальном времени (`r_deferred_water_reflect_all` 1, решается при загрузке материала; смена конвара перезагружает материалы `mat_reloadmaterial water`). ~1-1.5 мс на demo_map.
  - ps_2_b: не больше 4 уровней зависимых чтений текстур (X4018) - координаты выборки света не должны зависеть от выборки преломления; в комбо `BLURRY_REFRACT` свет читается одной выборкой.
- **Отражения (вода, зеркала) брали «запасной» свет всегда.** В `composite_ps30` (REFLECTVIEW) проверка «точка на экране основного вида» была `saturate( uv ) - uv == 0`: два `uv` этой разности получались разными инструкциями (mul и mad) и не сокращались точно - условие не выполнялось ни для одного пикселя, и любое отражение освещалось плоским светом без теней (стена в тени в отражении была в ~8 раз ярче самой стены). Теперь сравнение через `step`; запасной свет - небо (x `GetGISkyBoost`) + 0.6 солнца по нормали грани (из производных позиции, к камере вида). `r_deferred_reflect_debug 1` (в `mat_showwatertextures 1`: красный - свет найден в основном виде).

- **Ветер: деревья и трава** (`r_deferred_treesway`, `_strength`, `_speed`, `_calm` 0.16, `_leaves` 0.55, `_branches` 6, `_trunk` 0.4). Модели: статик-комбо `TREESWAY` в `gbuffer_vs30`/`composite_vs30`/`shadowpass_vs30` (`hl2rpm_sway_fxc.h`, константы VS c56/c57 — три прохода обязаны совпасть до бита: композит проверяет глубину G-буфера; тени качаются вместе с деревом). **Ствол почти стоит** (наклон верхушки `_trunk` ед. на 100 ед. высоты в сильный ветер — «стволы шевелятся как листва» было при общем изгибе всего дерева), **качаются ветви** — тем сильнее, чем дальше от оси ствола (ось z модели; у ствола 0, полностью — дальше 176 ед.), каждая в своём ритме по направлению от ствола и высоте (гладкая функция направления: фаза по `atan2` рвала карточки ветки на линии его разрыва), на концах — дрожь листьев. - **Просвечивание листвы и ткани** (`r_deferred_transmission`, `_power` 3, `_tint` 0.65, `_glow` 2, `_composite` 0.3; `$pbr_transmission`; `r_deferred_foliage_light` 0.7, `_depth` 100): листва (alpha-test материалы растительности) получает `$litface 1` (свет с обеих сторон). **Свет сквозь крону** — в проходе солнца (`lightingpass_global_ps30`, c80): для litface-пикселей затенённая часть получает `доля листвы среди блокеров × exp2(−глубина/100 ед.) × 0.7` солнца (глубина — до тенеобразователей из поиска блокеров PCSS; только ближние каскады, где есть поиск). **Листва помечена в «сырой» глубине атласа солнца**: `shadowpass_ps30` прибавляет c1.x = 2 у litface-тенеобразователей (`defpass_shadow.cpp`, на каждый draw; только каскады солнца — карта дождя и лампы получают 0), поиск блокеров декодирует `frac( raw·0.5 )·2` и считает листья как `raw − d` — свет идёт сквозь листья, но не сквозь стену, крышу или ствол (раньше куст в тени стены в 50 ед. получал ~23 % солнца). Другие формы этого декодирования (`step`, `float3`-аккумулятор, `[loop]`) и любой отладочный вывод листвы в этом шейдере дают **X4505** — регистров нет совсем. **Свечение против солнца** (2026-10-17, «не вижу подсветку листвы»): в проходе солнца к свету листа добавляется `дошедший свет × r_deferred_transmission_glow × (cos^3 + 2·cos^18)` угла «взгляд — солнце» (композит умножает на альбедо — свечение в цвет листа); прежний множитель композита (c33/c34, `1 + T·(…)`) оставлен на 0.3 — только оттенок. Против низкого солнца ветки светятся жёлто-зелёным; когда солнце за плотной кроной — светится край кроны и просветы, середина остаётся тёмной, как в жизни. Двусторонняя ткань моделей (curtain/cloth/tarp/flag…) — 0.3.
- **Occlusion culling** (2026-10-12; `deferred/deferred_occlusion.cpp`, `r_deferred_occlusion`, `_max` 320, `_distance` 5000, `_debug` 1 статистика раз в секунду / 2 ничего не прятать / 3 показать боксы спрятанного). Каждый кадр до 320 самых «крупных на экране» непрозрачных плоских граней мира (список окклюдеров собирает `deferred_worldmesh.cpp`: ≥ 2048 ед.², ≤ 12 вершин) растеризуются на CPU в буфер 256×144 (1/глубина, ~0.25 мс). Рендерабл, чей мировой AABB целиком за стенами, не попадает в списки **основного** вида (`CollateRenderablesInLeaf` в `clientleafsystem.cpp`, флаг `DeferredOcclusion_SetCollecting` ставит `DrawSetup` только когда вид не теневой и камера та же, что у буфера), лампа со спрятанным боксом не получает ни прохода, ни карт теней (`CullLights`). Теневые виды, 3D-скайбокс и отражения не трогаются. Консервативность: контур стены ужат на пиксель, глубина — дальняя в пределах пикселя, бокс расширен на пиксель и берётся по ближнему углу; **швы между гранями одной стены (общее ребро, та же плоскость и сторона) не ужимаются** — vbsp режет стену на много граней, и щель на каждом шве «просвечивала» бы всё. На demo_map_rus прячется ~35 % боксов; выигрыш во времени зависит от того, что спрятано (лампы с тенями — миллисекунды, мелкие пропы — в пределах шума).
- **Occlusion culling для открытого мира** (2026-10-30; карты без areaportals/hint/skip, мир в одной sky-коробке — PVS такой карты пропускает почти всё). Дополнения к абзацу выше:
  - **Сам мир**: движок рисует листья BSP с пометкой `leaf->visframe == r_visframecount` (`gl_rsurf.cpp`, `mod_vis.cpp` слива). `DeferredOcclusion_HideWorldLeaves` / `_RestoreWorldLeaves` вокруг `BuildWorldRenderLists` основного вида (`CBaseWorldViewDeferred::DrawSetup`; не теневые виды, не отражение) снимают пометку с закрытых листьев и сразу возвращают — между кадрами ничего не хранится (кэш `Map_VisMark` не ломается). Массив `mleaf_t` движка (64 байта, `visframe` +4, `cluster` +48) ищется в `model_t` мира (модель 1) по `worldbrushdata_t` (`numsubmodels`/`numplanes`/`numleafs` = лумпам `.bsp`) и проверяется лист за листом (`contents`, `cluster`); не совпало — функция выключена с предупреждением. Память движка читается только через `RPMCrash_IsReadable` (VirtualQuery): исключение поймал бы VEH отладчика крашей. **Лист проверяется по тому, что из-за него рисуется**, а не по объёму (листья воздуха тянутся до потолка sky-коробки): его грани, обрезанные боксом листа (лист перечисляет все грани, которых касается), куски дисплейсментов (их движок привязывает к листам по боксу), detail props (+64/+128 ед.), и **все рендереблы листа** (`ClientLeafSystem_AreRenderablesInLeafHidden`, границы размещения `_Fast` — без костей родителя): список листьев вида — это и источник рендереблов. Тест листьев — по пирамиде буфера (min 1/глубины 2×2, уровень, где бокс ≤ 8×8 текселей, `IsBoxHiddenCoarse`). На `rpm_trainstation_testoptimization` прячется 5–60 % листьев PVS, ~0.2–0.75 мс; пиксельный A/B на 16 видах — только шум, анимированные экраны и провода.
  - **Лампы по листьям** (`DeferredOcclusion_AreLeafPartsHidden` в `CullLights`): лампа не рисуется, если часть её бокса в каждом её листе (∩ бокс листа) закрыта или лист вне PVS — один бокс на весь радиус почти никогда не закрыт целиком. Это и дало выигрыш: точка 18 серии — 17.2 мс против 24.0. Список листьев лампы обрезан на `DEFLIGHT_MAX_LEAVES` (128): с неполным списком ни этот тест, ни старый тест PVS (`AreAnyLeavesVisible`) не применяются — видимые листья могли оказаться за обрезкой. На бюджет теней ламп отсечение не действует (тень не должна «проявляться» за 0.5 с из-за поворота камеры).
  - **Окклюдеры** (`deferred_worldmesh.cpp`): (1) **нормаль грани — `planes[planenum]` без переворота по `side`** (vbsp пишет в `planenum` собственную плоскость грани, `side` — лишь «повёрнута относительно плоскости узла»): переворот делал половину стен карты «смотрящими от глаза» — они никогда не были окклюдерами (буфер на виде в стену был покрыт на 18 %); (2) вершины на прямых сторонах (T-стыки vbsp: у длинной стены их десятки) выбрасываются до проверки предела 12 вершин — только выпуклые или отстоящие < 0.02 ед. (окклюдер не больше стены), склеенная сторона — шов, только если все её рёбра общие; (3) **треугольники дисплейсментов** (≥ 512 ед.²) — тоже окклюдеры (холмы), внутренние рёбра сетки — швы, сторона — по нормали грани-основы (сзади дисплейсмент прозрачен).
  - Отладка: `r_deferred_occlusion_debug 1` (строка раз в секунду: стены, боксы, листья, лампы), `3` (боксы скрытого: красный — рендереблы, синий — листья, жёлтый — лампы), `4` (контуры стен, попавших в буфер), `r_deferred_occlusion_save` (буфер в `occlusion_buffer.pgm` папки мода). `r_deferred_occlusion_world 0` выключает листья и лампы по листьям.

  - **Списки мира движка по мешам** (2026-10-30, `deferred/deferred_worldlists.cpp`, `r_deferred_worldlists_sort`; «здания в конце улицы пропадают, в консоли бесконечно Too many vertex format changes»). - `CFourWheelVehiclePhysics::Initialize` отказывается создавать колёсную машину на модели без аттачментов `wheel_*` (на `map_v11` декоративная `car004a` как `prop_vehicle` взрывала vphysics через ~10 с после загрузки).

## Без костюма HEV: пульс в HUD и «раненый» взгляд

Задумка пользователя: без костюма нет цифр — HUD показывает то, как герой себя чувствует (рисовка HL2, минимализм); краснота экрана — по краям, как в COD4, с венами; при совсем малом здоровье — покачивание, затуманивание, волны темноты. Сделано 2026-10-30.

- **Логика** — `game/client/hl2rpm_vitals.cpp` (`CAutoGameSystemPerFrame`, каждый кадр): доля здоровья = здоровье / максимум. `m_iMaxHealth` теперь уходит клиенту (`DT_BasePlayer`, `IMPLEMENT_NETWORK_VAR_FOR_DERIVED( m_iMaxHealth )` в `player.h`): `C_BasePlayer::GetMaxHealth()` раньше возвращал 1. Пульс 64 → ~146 уд/мин к нулю здоровья, +38 «адреналина» после удара (спадает ~9 с); ниже 25 % ритм сбивается, изредка ранний удар. Кардиограмма — 250 отсчётов/с, развёртка 1.6 с (400 отсчётов): QRS прямыми с острыми углами, P/T — горбы, быстрое сердце сжимает форму (√RR), хвост прошлого удара доигрывается (ранний удар не рвёт линию).
- **HUD** — `game/client/hl2/hud_vitals.cpp`, элемент `HudVitals` в `scripts/HudLayout.res` мода на месте `HudHealth` (копия — `hl2rpm_extras/scripts`): коробка HL2 (`PaintBackgroundType 2`, `BgColor`), развёртка слева направо — новое ярко, прошлый проход тускло, зазор перед «пером». Линия — меш (`vgui/white`, свечение `vgui/white_additive`) в **абсолютных координатах экрана** (`ipanel()->GetAbsPos`): MatSystemSurface сдвигает на место панели только свои примитивы, матрицу не трогает. Лента с общими рёбрами и митрами на углах — отдельные квады сегментов дают яркие узлы на полупрозрачном следе. Цвет: белый → жёлтый HL2 (0.48) → оранжевый (0.28) → красный (≤ 0.12). Удар — вспышка `DamagedBg`, ниже 25 % коробка пульсирует красным на каждом ударе (как стоковый `HealthPulse`).
- **Экран** — `hl2rpm_lowhealth_ps30` (`HL2RPM_LOWHEALTH` в `stdshaders/hl2rpm_postfx.cpp`; значения — переменные материала, без `IDeferredExt`, работает и с `-nodeferred`). Вызов после `DeferredPostFX_Draw`, до затемнений движка и HUD (в стоковом `viewrender.cpp` — перед `ViewDrawFade`); при полном здоровье проход не рисуется. Красное ползёт с краёв (скруглённый прямоугольник, край ломают пятна канала b), вены растут от краёв в порядке канала g текстуры `materials/hl2rpm/effects/lowhealth_veins.vtf` (генератор `hl2rpm_extras/tools/make_vitals_assets.py`: ветвление по закону Мюррея, сужение к кончикам), на ударе сердца набухают, кадр чуть «вздувается». Ниже 25 % — волны «обморока» 2.5–4.5 с: размытие (кадр → `_rt_SmallFB0` 4×4 + tent; блум движка к этому моменту отработал), обесцвечивание, темнота от краёв. Покачивание: крен — только на экране (`HL2RPM_Vitals_ApplyView` в `CalcPlayerView`: центр экрана, где прицел, не сдвигается), тангаж/рыскание — смещение прицела в `ClientModeShared::CreateMove` (прибавляется разность с прошлого вызова: туда приходят и покадровый `ExtraMouseSample`, и потиковый `CreateMove`); не в меню, диалогах, транспорте. Смерть: красное остаётся, за 2.5 с темнеет (поверх всё равно стоковый `HudPlayerDeath` из hudanimations HL2 — экран за 4 с заливается красным, так было и раньше). Цена прохода — ~0.45 мс (40 %, без размытия) / ~0.5 мс (6 %, с размытием) на GTX 960M в 1600×900 (A/B `cl_vitals_screen 1/0` в одном запуске); при здоровье ≥ 70 % проход не рисуется.
- **Звук**: дыхание `player/breathe1.wav` (петля, `CSoundPatch`, громкость и высота плавно) ниже 60 % и после ударов; сердце ниже 45 % — `sound/hl2rpm/player/heartbeat_once.wav` (один удар из зацикленного стокового `heartbeat1.wav`, тот же скрипт) на каждом зубце R. Писк костюма `HUDQuickInfo.LowHealth` без костюма не звучит.
