Visual checks go through the `hl2rpm-playtest` skill (`scripts/run_game.ps1 -Map <map> -Steps "<flags>|<commands>"`): it drives the in-client photo tour, writes screenshots/*.jpg and `[tour]` FPS lines, and backs up/restores cfg/config.cfg. Menu/VGUI can't be captured with `jpeg` (black) — `-CaptureAfter` / `ui_clicks.ps1` use PrintWindow from a DPI-aware process. Tour steps survive map changes (`|map demo_map_rus` with `+cl_weather_tour_step 15`) — that is the map-change/reload stress test.

Lessons from the 2026-09-30/10-01 rendering work:
- Static screenshots miss most real bugs the user reports (flicker, crawl, view-dependent effects). Record consecutive frames: `host_framerate 0.016667; startmovie <p> tga` (tga, not jpg — jpeg blocks flicker at edges), then `hl2rpm_extras/tools/crawl_stats.py` (second difference: ignores smooth motion, shows flicker) with A/B toggles in the same run.
- Bugs that depend on what was seen first (per-material caches) need a deterministic setup: copy the map, `bsp.py setkv` the info_player_start to face the trigger (e.g. water), test, delete the copy and its .ain.
- `[tour]` timing lines exist only for `shot` steps and drift ±1.5 ms between identical steps — alternate A/B/A/B before claiming a perf win.
- Stock EP1/EP2 maps from the reference folder run in the mod: copy temporarily into hl2rpm\maps for conversion/open-world tests (ep2_outland_07), delete the .bsp and maps\graphs\*.ain afterwards.
- Injected keys can't open the console; GameUI-visible situations are tested with `gameui_activate`/`gameui_hide` steps + `-CaptureAfter`.
- Heap corruption: staged checks narrow it to a frame/pass, then a cdb hardware write watchpoint (`ba w4`) on the corrupted address names the writer in one run (details in CLAUDE.md "Отладчик крашей"). This found the shader API's 32-register pixel constant arrays overflowing (fixed by hl2rpm_psconstants.cpp).

- Isolate by toggles before theorizing: `r_3dsky 0` (what is skybox), `r_csm_color 1` (which pixels get cascades), `r_flex 0` / `r_eyes 0` (face bugs), `-Extra "-nodeferred"` (stock reference of the same view), a throwaway map from `new_test_map.py` for a clean A/B (lamp behind a wall, glass in front of the sky). The Alyx eye gap was found this way in a few runs after hours of reading code.
- GPU cost: compare the same view at two resolutions/settings — cost independent of screen size points at shadow-map passes (the point light cube faces cost ~1.5 ms each until their shader stopped writing depth).

Pitfalls seen:
- FCVAR_ARCHIVE convars passed on the command line (`+cl_weather 0`, `+rpm_crash_handler 0`, `+cl_options_graphics_page 0`, `+mat_queue_mode 0`) are saved into the mod's cfg/config.cfg — this silently disabled rain/weather/the options page and the crash debugger for the user. Pass only non-archived convars, or restore config.cfg after testing (run_game.ps1 does). Changing an archived convar's meaning needs a rename (old values stay in config.cfg).
- Delete test cfgs / debug materials / screenshots / temp maps from the mod folder afterwards: it is zipped as-is for releases.
- The old "exit crash in filesystem_stdio" and the map-change / mat_reloadallmaterials crashes were the pixel-constant overflow — since 2026-10-01 quit exits with code 0. A new crash there means heap corruption again.
- map_v11 starts on a black screen (scripted intro) and its `prop_vehicle` car004a used to crash vphysics — now refused in code, the map itself still should be fixed in Hammer.
- The crash debugger opens Notepad with the analysis after a crash — the user's Notepad may have their own tabs, never kill notepad.exe.
- 2026-10-10: piping `run_game.ps1` into `Select-Object -First N` stopped the script at its N-th output line, before it restored config.cfg — the user's config kept my test values (`r_hl2rpm_lens 0`, `r_weather_motes 0`) and my next test silently ran with them. The script now restores before printing anything, but never cut its output short; after any odd run check config.cfg and `%TEMP%\hl2rpm_config_backup_*.cfg` (a leftover file there is the clean pre-run config).
- Screenshot tools lie about tiny things: 1-2 pixel moving specks (dust motes) vanish in downscaled JPEG sheets while the user sees them live. Measure such effects with lossless `startmovie <name> tga` frames against an "effect off" baseline before claiming "not drawn".
- Tour steps: set the camera (`setpos/setang`) in every step line, including the one with `startmovie`; positions from one map variant (demo_map) are outside the level in another (demo_map_rus: spawn 865 586 -398). The `fov` cheat changes the player's default FOV (not a zoom); weapons/suit come through the inventory (`inventory_add weapon_smg1; inventory_use weapon_smg1`, `inventory_add item_suit; inventory_use item_suit; +zoom`).
- Shell: a Python heredoc in the Bash tool turns `\\n` inside C string literals into a real newline, and a long heredoc full of quotes can fail to parse at all — write such patches with the Edit tool or as a script file (Write, then run).
- Engine video settings live in the registry (`HKCU\Software\Valve\Source\<mod path>\Settings`, e.g. `mat_antialias`); Git Bash needs `MSYS_NO_PATHCONV=1` for `reg query ... /v`. Restore anything changed there for a measurement.

- 2026-10-10, the day after a release the user found 17 bugs my tests had passed. What the tests lacked (do these before calling visual work done):
  - **HUD on, no weapon, a VGUI panel open** (`cl_drawhud 1; r_deferred_timecycle_editor` in a `shot` step - jpeg shots include VGUI in game). The tour runs with `cl_drawhud 0` and I often held a weapon: its composite reset a constant the black UI depended on.
  - **The first second after a spawn/teleport and a walk**, not a still after a 6 s wait: put `cl_weather_tour_step 0.4` in the step before a `shot` step that teleports; for walks `noclip; sv_noclipspeed 0.65; +forward` (~190 u/s) and compare `r_deferred_gi_stats` before/after ("worst ... ms", pending). Debug views that color the data source (`r_deferred_gi_debug 5`) show holes a normal frame hides.
  - **Far away** (> 700 units), from above, and **demo_map in the rain**: seams of a system's range and things drawn after the weather pass only show there. `r_csm_pcss 8` tells what is not in the G-buffer.
  - Bisect a broken look with one toggle per `shot` step in a single run (`r_weather_motes 0`, then `r_hl2rpm_post 0`...): found the black UI in one run.
  - A crop zoomed 3x (`cropstack.py`) per toggle shows 1-2 pixel artifacts (edge lines) the sheet hides.
- `run_sheet.ps1` (scratchpad wrapper) only collects `<map>*.jpg`: shots taken after a `map` change stay in the mod's `screenshots` - move them out.
- Shader pitfalls met that day: `lightingpass_global_ps30` has no temp registers left (X4505 on any addition; a failed compile deletes the `.vcs` in the source tree - restore with a recompile); `materials->FindMaterial` on a name that is not loaded reads the disk mid-frame (check `IsMaterialLoaded`).

- Lessons of 2026-10-11 (water / PBR session): (1) **compare against the stock renderer on a purpose-built map** (`water_test`: stock materials at known depths, the map sun matched to the deferred sun of 13:00, `-Extra "-nodeferred +sv_weather_procedural_sky 0"`) - the existing maps had only shallow water and hid that every water had lost its color; (2) after long shader compiles the laptop throttles: frame times of separate runs differ by 2-4 ms - measure a cost by alternating the convar A/B/A/B inside one run; (3) look at render targets directly (`mat_showwatertextures 1`) and add a debug output to the shader before theorizing: the reflection views had been lit by the flat fallback light since they were written, because of an exact float compare; (4) `composite_ps30` takes ~8 minutes to compile - batch its changes, tune with constants; run it in the background and keep working.

- Lessons of 2026-10-17 (user's screenshot report): (1) the user's setpos/setang lines identify the map by the props in view (`bsp_props.py` per map) - reproduce exactly there; (2) a feature "not visible" for the user can be **off in their config.cfg** (`r_deferred_pom "scale"`, a console typo saved as an archived value) - grep config.cfg for the feature's convars first; (3) "wrong color" bugs: the stock renderer (`-nodeferred`) on the same view shows the intended colors, then bisect with one toggle per shot (`r_deferred_envmap_fallback 0` found the white Metrocop in one run); (4) `console.log` accumulates all sessions - count errors only after the session's own start line, or old lines look like new ones.

**Why:** the user can't be asked to test each iteration; these tools and caveats save hours next time. Related: [[user-hardware]], [[hl2rpm-big-request-status]].
- Lessons of 2026-10-18: (1) pixel A/B of a still is meaningless while things sway - freeze `r_deferred_treesway 0` (trees and grass), `r_deferred_taa_jitter 0`, `r_weather_motes 0`, `r_weather_cloud_wind_scale 0`, shoot A, B, A and compare B-A against the A/A noise floor (~3 levels; swaying grass alone gives ~8); (2) a setting that only shows against the sun (leaf glow) must be shot at several times of day - at the user's view the sun was behind a dense crown at 13:00 and the effect was nearly invisible there, obvious at 9:00 and 16:30; (3) perf A/B between *processes* (different d3d9.dll) - alternate A,B,A,B in one script and also run at 800x450 to tell GPU from CPU; (4) `lightingpass_global_ps30` has no temp registers left - even a debug return fails with X4505, test shader variants as throwaway copies (`<name>_ps30.fxc` copies compile in seconds when they fail).
- Lesson of 2026-10-30 (missed overnight, the user found it next morning): an on/off A/B of a feature is blind to an engine error present in both runs - "Too many vertex format changes in frame, whole world not rendered" spammed in every step of the culling A/B and my log filter (`error|warning|fail`) did not match it. After any run read the **count of each distinct console line per step** (echo a marker per step, awk count) and look at the far end of the view for missing geometry, not only at the difference between A and B.
- Lesson of 2026-10-30 (GI "loading in chunks"): (1) anything computed in the background on wall-clock time can't be judged from a `startmovie` recording (the game runs at ~6 fps there, the workers finish everything) - capture the window in real time with `capture_rt.ps1` (playtest skill); (2) the same world point looks brighter or darker from another camera place because of the frame's exposure (and `r_hl2rpm_post 0` turns the engine's own exposure on) - compare a system's debug output (`r_deferred_gi_debug 10`), not the final frame, before calling something "camera dependent"; I spent an hour on a "dark sphere" that was a roofed floor plus exposure.
